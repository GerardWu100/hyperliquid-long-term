How the Hyperliquid candle collector works

A plain-English guide to the service, its data flow, and its main design choices.

How to use this

The sections follow one ingestion cycle from start to finish. Code snippets are copied unchanged from src/hyperliquid_candles/. Numbers in grey Sample data boxes came from running the code on 10 August 2026 against Hyperliquid's public endpoint and the project's ClickHouse server. Coloured boxes mark design choices, traps, and known weaknesses.

The process in plain English

Hyperliquid is a crypto derivatives exchange. Its public interface serves only the latest few thousand one-minute price bars for each market. This service keeps a copy: every half hour it asks the database for each market's newest stored bar, requests the later bars from Hyperliquid, and writes them back. Over time, the database keeps history the exchange no longer serves. The database is the only memory between cycles, so the service can restart without losing its place.

01The goal and the rule it follows

A candle, or bar, summarises one time slot with six numbers: the first traded price (open), highest and lowest prices (high, low), last price (close), traded amount (volume), and trade count. This project collects one-minute candles for Hyperliquid's perpetual markets. A perpetual is a derivative contract that tracks an asset's price and has no expiry. Traders often call one a "perp".

Hyperliquid's public request-and-response interface provides only the most recent 5,000 candles per market. At one minute per candle, that is about three and a half days. Older data disappears from the interface. The project's job is simple: stay online and copy each recent window into the database before it disappears.

The one rule: the database is the only memory

The service keeps no state between cycles: no watermark file, cache, or in-memory bookmark. Each cycle runs SELECT symbol, max(open_time) ... GROUP BY symbol against ClickHouse and builds its plan from that result. If the process stops during a write, the next cycle sees an older maximum and fetches those minutes again. There is no watermark table because a second record of progress could disagree with the stored rows.

Vocabulary used throughout this page

ClickHouse is the database: a column-oriented store for large analytical tables. This project expects it to already exist. A watermark is the newest open_time stored for one symbol. REST, short for Representational State Transfer, means the ordinary request-and-response web interface rather than a streaming connection. The horizon is the oldest candle Hyperliquid still serves. Idempotent means that repeating an operation has the same result; inserting the same candle twice still leaves one candle.

Why the file beats the environment

This reverses the usual rule, where an exported shell variable overrides a file. A password containing a dollar sign can be changed by shell expansion, making a mangled password look incorrect. With the file taking priority, the service uses the value shown in .env.

Trap: the critical threshold is not arbitrary

alert_critical_min = 4320 is 72 hours. The recoverable horizon is 4,999 minutes, or 83.3 hours. The alarm fires about eleven hours before the oldest missing minute becomes unrecoverable. If rest_horizon_candles changes, this threshold should change too; the code does not enforce that link.

Where the project root comes from

PROJECT_ROOT = Path(__file__).resolve().parents[2] in config.py walks from src/hyperliquid_candles/config.py to the repository root. Commands therefore work from any directory. The environment variable HL_DATA_DIR moves writable files, including logs and an optional replacement config.toml; the Docker image sets it to /data. It must come from the process environment, not .env, because the loader needs the directory before it can read files.

run_scheduler — sleep, but stay interruptible

    while not stop_requested:
        try:
            cycle_callback()
        except Exception:
            # A single cycle failure (network blip, transient ClickHouse error)
            # must not kill the long-running loop. Log it and continue to the
            # next scheduled tick; ClickHouse rows remain the source of truth, so
            # the next cycle recovers any missed window from stored watermarks.
            LOGGER.exception("Ingestion cycle failed; continuing to next cycle")
        jitter_seconds = random.uniform(
            0, min(30, settings.ingestion.poll_interval_sec / 10)
        )
        sleep_seconds = settings.ingestion.poll_interval_sec + jitter_seconds
        LOGGER.info("Sleeping %.1f seconds before next ingestion cycle", sleep_seconds)

        deadline = time.monotonic() + sleep_seconds
        while not stop_requested and time.monotonic() < deadline:
            # The clock advances between the loop test and this line, so the
            # remaining time can already be negative. `time.sleep` raises on a
            # negative argument, which would kill the service loop, so clamp it.
            remaining_seconds = deadline - time.monotonic()
            time.sleep(max(0.0, min(1.0, remaining_seconds)))
In plain words

Run the work, log failures, and wait in one-second pieces so shutdown is noticed within about a second.

What it does

Input: settings and a function to call each cycle. Output: nothing; it returns when a stop signal arrives. Role: the outer loop for the long-running service.

Why the sleep is chopped into one-second slices

signal.signal sets a flag, but time.sleep(1800) would not check it until the full wait ended. One-second slices let docker compose down or Ctrl-C finish in about a second. time.monotonic() avoids a system clock adjustment making the wait last too long.

Why the jitter

random.uniform(0, min(30, interval/10)) adds up to thirty seconds of random delay. Without it, services restarted at the same time would keep sending requests in lockstep. The thirty-second cap is fixed in the code rather than configurable.

04Choosing which markets to collect

def active_perp_symbols(meta_response: dict[str, Any]) -> tuple[str, ...]:
    """Return active perpetual symbols from a Hyperliquid `meta` response.

    Hyperliquid names perpetual markets in `universe`. Delisting flags are not
    always present, so the parser treats missing flags as active.
    """
    raw_universe = meta_response.get("universe", [])
    if not isinstance(raw_universe, list):
        raise ValueError("Hyperliquid meta response has no universe list")

    symbols: list[str] = []
    for item in raw_universe:
        if not isinstance(item, dict):
            continue
        symbol = item.get("name")
        is_delisted = bool(item.get("isDelisted", False))
        if isinstance(symbol, str) and symbol and not is_delisted:
            symbols.append(symbol)

    return tuple(sorted(set(symbols)))
What it does

Input: the JavaScript Object Notation (JSON) object returned for a meta request. Output: a sorted tuple of unique market names. Role: builds the work list for the cycle.

The database holds 180 symbols, but only 177 are active today. The other three were delisted after collection. Their history remains, but the service no longer updates them.

Why sorting matters more than it looks

The exchange returns markets in its own order, starting with BTC. Sorting gives each cycle the same work order, which makes logs easier to compare. Applying set() before sorted() also prevents a repeated name from being fetched twice.

Trap: a missing flag means active

item.get("isDelisted", False) treats a missing flag as "still trading". That is safer here: one unnecessary request costs little, while dropping a live market can lose unrecoverable data. If Hyperliquid renames the field, however, delisted markets will quietly return to the work list.

Allowlist mode fails loudly

In allowlist mode, select_symbols raises ValueError if a requested name is not active. A typo in config.toml stops the cycle instead of silently collecting three markets when you requested four. Verified live: select_symbols(meta, "allowlist", ("BTC", "ETH")) returned ('BTC', 'ETH').

05Time arithmetic

Inside the service, timestamps are integers: Unix epoch milliseconds, the number of milliseconds since midnight Coordinated Universal Time (UTC) on 1 January 1970. They become Python datetime values only at the ClickHouse boundary. Integers compare exactly and do not carry timezone ambiguity.

last_closed_open_ms — never store a bar that is still forming

def last_closed_open_ms(now_ms: int | None = None) -> int:
    """Return the open time of the latest fully closed 1-minute candle."""
    effective_now_ms = now_ms
    if effective_now_ms is None:
        effective_now_ms = int(datetime.now(tz=UTC).timestamp() * 1000)
    current_minute_open_ms = effective_now_ms // INTERVAL_MS * INTERVAL_MS
    return current_minute_open_ms - INTERVAL_MS
The formula

$$t_{\text{last}} \;=\; \left\lfloor \frac{t_{\text{now}}}{\Delta} \right\rfloor \Delta \;-\; \Delta$$

$t_{\text{now}}$ is the current time in Unix epoch milliseconds. $\Delta = 60{,}000$ is one minute in milliseconds, represented by INTERVAL_MS. The floor bars $\lfloor \cdot \rfloor$ mean "round down to a whole number", so $\lfloor t_{\text{now}}/\Delta \rfloor \Delta$ is the start of the current minute. Subtracting one more $\Delta$ selects the latest completed minute. $t_{\text{last}}$ is the newest candle open time the service requests.

Trap: this single line is what keeps the data honest

At 22:51:47 the 22:51 candle is still changing. Storing it would make the database's "22:51 close" depend on when the request happened, not on the finished minute. A trading test could then use a price that was not known at the time, a look-ahead error. Subtracting one interval ensures that only completed minutes are written.

The formula

$$t_{\text{floor}} \;=\; t_{\text{last}} \;-\; (N-1)\,\Delta$$

$N$ is rest_horizon_candles, the number of candle slots in the window, including both ends. $t_{\text{floor}}$ is the oldest opening time. The $N-1$ accounts for the intervals between the candles: five candles have four intervals between their opening times.

build_incremental_work_items — one window per stored market

The formula

$$s \;=\; \max\!\bigl(w - k\Delta,\; t_{\text{floor}}\bigr), \qquad e \;=\; t_{\text{last}}$$

$w$ is the watermark, the newest opening time stored for the market. $k$ is overlap_candles (5 by default), so $w - k\Delta$ begins five minutes before that watermark. $t_{\text{floor}}$ is the horizon from the previous formula; the $\max$ prevents requests for data the exchange cannot serve. $[s, e]$ is the inclusive window requested for the market.

Why refetch five minutes you already have

The exchange can revise a candle shortly after it closes, and a cycle can stop between fetching and inserting. Requesting the last five minutes again covers both cases. Repeats are safe because of the database key. The cost is a small number of duplicate rows waiting for a merge: 4,965 out of 13 million, or 0.04 per cent.

06Talking to Hyperliquid

candle_request_weight — guessing the bill before you order

Hyperliquid limits weight, a cost assigned to each call, rather than simply counting calls. The published ceiling is 1,200 weight per minute per internet address. A candleSnapshot call costs 20 plus one for every 60 candles returned.

    requested_slots = (end_ms - start_ms) // INTERVAL_MS + 1
    return BASE_INFO_WEIGHT + requested_slots // ITEM_WEIGHT_BLOCK
The formula

$$n \;=\; \frac{e-s}{\Delta} + 1, \qquad W \;=\; 20 \;+\; \left\lfloor \frac{n}{60} \right\rfloor$$

$s$ and $e$ are the requested window bounds in milliseconds. $n$ is the number of minute slots requested, and $W$ is the estimated weight. The constants 20 and 60 are BASE_INFO_WEIGHT and ITEM_WEIGHT_BLOCK. The exchange charges for candles returned, never more than requested, so this estimate is conservative.

TokenBucket — a tap that refills at a fixed rate

    def wait_for(self, weight: float) -> None:
        """Block until at least `weight` request tokens are available."""
        if weight <= 0:
            raise ValueError("weight must be positive")

        while True:
            self._refill()
            if self._tokens >= weight:
                self._tokens -= weight
                return

            missing_tokens = weight - self._tokens
            tokens_per_second = self.tokens_per_minute / 60.0
            time.sleep(missing_tokens / tokens_per_second)
In plain words

The bucket gains tokens at a steady rate. Each request spends tokens before it is sent. If too few are available, the caller waits for the missing tokens.

The formula

$$T \leftarrow \min\!\left(C,\; T + (\tau - \tau_{\text{prev}})\frac{B}{60}\right), \qquad \text{wait} \;=\; \frac{W - T}{B/60}$$

$T$ is the current token count, $C$ is the capacity (equal to $B$ unless changed), $B$ is weight_budget_per_min, and $\tau$ and $\tau_{\text{prev}}$ are consecutive readings of a steadily increasing clock in seconds. $W$ is the request weight. The first expression adds tokens for elapsed time and caps the result at capacity. The second gives the wait when the bucket is short.

Why the weight is reserved before sending, not after

The client calls rate_limiter.wait_for(request_weight) inside the retry wrapper, before the Hypertext Transfer Protocol (HTTP) call. Charging after the response arrives would let a cold start send many requests at once before discovering that it overspent. Reserving first paces the initial burst too.

The weakness, stated honestly

The bucket starts full. Its capacity defaults to one full minute of budget, so a new process can spend capacity plus refill in its first minute: 1,000 + 1,000 = 2,000 weight against the exchange ceiling of 1,200. Retries absorb the refusals, but the limit is not guaranteed. The project's notes.md suggests capping capacity so that capacity plus budget stays below 1,200. That change has not been made.

_post_info_with_retry — what counts as worth retrying

        @retry(
            retry=retry_if_exception_type((httpx.HTTPError, RuntimeError)),
            stop=stop_after_attempt(self.max_retries),
            wait=wait_exponential_jitter(initial=1, max=30),
            reraise=True,
        )
        def _send() -> Any:
            # Reserve the full estimated weight before each attempt. Charging
            # response-item weight afterwards permits an initial burst that can
            # exceed the configured per-minute budget.
            self.rate_limiter.wait_for(request_weight)
            response = self._client.post(self.base_url, json=payload)
            if response.status_code == 429 or response.status_code >= 500:
                raise RuntimeError(
                    f"Transient Hyperliquid status {response.status_code}: {response.text[:200]}"
                )
            response.raise_for_status()
            return response.json()
What it does

Input: a JSON request body and estimated weight. Output: the decoded JSON response. Role: the shared path for every exchange call.

Status 429 means "too many requests"; 500 and above mean a server error. Both become RuntimeError so the retry decorator handles them. Other errors, such as a 400 for a malformed request or a 404, pass through raise_for_status() as httpx.HTTPStatusError. They are retried because they inherit from httpx.HTTPError, but retries cannot fix them, so they eventually surface.

Trap: the weight is paid on every attempt

wait_for is inside _send, so a request refused four times pays four times. That matches the exchange's charging rule, but a failing connection can use budget that healthy markets must wait for.

Why check things that "cannot" be wrong

A valid bar cannot have a high below its open, so these checks may look unnecessary. They catch exchange changes, such as a renamed field, new interval string, or unit change, as an immediate per-market failure instead of silent table corruption.

Trap: trades = 0 is normal, not missing data

Hyperliquid emits a candle for a minute with no trades. It carries the previous price forward, so open, high, low, and close are equal and volume is zero. The parser accepts these candles. In the live table, 2,380,174 of 13,002,252 rows, or 18.3 per cent, have zero trades. Treating them as ordinary price observations will understate movement in volatility or liquidity studies. This is a property of the data, not a collector bug.

dedupe_by_symbol_open_time

Input: candles from several possibly overlapping pages. Output: one sorted candle per (symbol, open_time_ms) pair. Role: prevents the same minute from being sent twice in one request. Verified: six rows in, three out. The dictionary keeps the last copy seen; because all copies come from the same source in the same cycle, the choice does not matter.

08Paging backwards

This is the key idea behind the collector.

Why forward paging cannot work here

If a requested window is wider than Hyperliquid's limit, the endpoint does not return the oldest part and stop. It returns the part nearest the end and silently drops the oldest overflow. Asking for "everything from ten weeks ago until now" and moving the start forward would therefore return the same recent chunk repeatedly. The fetcher moves the end backwards instead, requesting the next-oldest chunk each time.

    fetched_rows: list[Candle] = []
    cursor_end_ms = end_ms

    while cursor_end_ms >= start_ms:
        page = source.fetch_candles(
            symbol=symbol, start_ms=start_ms, end_ms=cursor_end_ms
        )
        if not page:
            break

        fetched_rows.extend(page)
        oldest_open_ms = min(candle.open_time_ms for candle in page)

        # The page already reaches the requested start, so the window is covered.
        if oldest_open_ms <= start_ms:
            break

        # Step the cursor to just before the oldest candle we just received so
        # the next request peels off the next-older chunk.
        next_cursor_end_ms = oldest_open_ms - interval_ms

        # Defensive guard: if the cursor did not move backward, the API is not
        # honouring endTime as expected. Stop rather than loop forever.
        if next_cursor_end_ms >= cursor_end_ms:
            break

        cursor_end_ms = next_cursor_end_ms

    return dedupe_by_symbol_open_time(fetched_rows)
In plain words

Request the window and find the oldest returned bar. Request again, ending one minute before that bar. Repeat until the requested start is reached or the exchange returns nothing new.

What it does

Input: a market name, an inclusive millisecond window, and an object with a fetch_candles method. Output: the candles in that window that the exchange still exposes, deduplicated and sorted; possibly an empty list. Role: the shared fetch function for initial backfill, incremental catch-up, and gap repair. Pagination has one implementation.

Why termination depends on the cursor, never on page size

"Stop when a page is smaller than the maximum" is unreliable: the exchange may change its page size, and some markets may have fewer bars. This loop stops when the page is empty, reaches the requested start, or the cursor fails to move backwards. The last check prevents an endless loop if the endpoint ignores endTime.

Trap: the loop can return fewer rows than asked for, silently

If the window extends past the horizon, the loop returns what exists without an error or warning. A ten-week-old gap cannot be recovered, and reporting it every cycle would add noise. Therefore, "fetched 40 rows" does not prove that 40 rows existed. The per-market status row keeps requested_start and effective_start separate so the difference remains visible.

09Reading and writing ClickHouse

The table, and why re-inserting is safe

CREATE TABLE IF NOT EXISTS {database}.candles_1m
(
    symbol      LowCardinality(String),
    open_time   DateTime64(3, 'UTC')  CODEC(DoubleDelta, ZSTD(12)),
    close_time  DateTime64(3, 'UTC')  CODEC(DoubleDelta, ZSTD(12)),
    open        Float64               CODEC(Delta, ZSTD(12)),
    high        Float64               CODEC(Delta, ZSTD(12)),
    low         Float64               CODEC(Delta, ZSTD(12)),
    close       Float64               CODEC(Delta, ZSTD(12)),
    volume      Float64               CODEC(ZSTD(12)),
    trades      UInt32                CODEC(T64, ZSTD(12)),
    inserted_at DateTime64(3, 'UTC')  DEFAULT now64(3) CODEC(DoubleDelta, ZSTD(12))
)
ENGINE = ReplacingMergeTree(inserted_at)
PARTITION BY toYYYYMM(open_time)
ORDER BY (symbol, open_time)
SETTINGS index_granularity = 8192
Reading this DDL

DDL means data definition language: SQL that creates tables. ReplacingMergeTree(inserted_at) is a ClickHouse table engine that eventually keeps the row with the larger inserted_at when rows share a sorting key. Here the key is (symbol, open_time), so each market-minute resolves to one row. CODEC selects a column's compression method. Delta stores differences from the previous value. DoubleDelta stores differences between those differences and works well for evenly spaced timestamps. T64 packs small integers, while ZSTD(12) provides general-purpose compression at a high setting. LowCardinality(String) stores repeated strings as dictionary IDs, which greatly reduces the space used by 180 market names repeated 13 million times.

Why volume alone gets no delta encoding

Prices usually change gradually, so differences between adjacent values are small and compress well. Volume can jump from near zero to a large value, so delta encoding may be as large as the original value and make the file bigger. The project measured this in COMPRESSION_BENCHMARK.md. All selected methods are lossless; changing volume to a 32-bit float was rejected because it would change the stored numbers.

Trap: "eventually" is doing real work in that sentence

ReplacingMergeTree removes duplicates during background merges, not during insertion. Until a merge runs, both rows appear in a plain SELECT. The live table has 4,965 duplicate keys. Research queries must collapse them with FINAL or argMax(column, inserted_at) grouped by (symbol, open_time). A plain count() or avg() is slightly wrong.

Reading the watermarks

def datetime_to_ms(value: datetime) -> int:
    """Convert a ClickHouse datetime value to Unix epoch milliseconds.

    The `candles_1m` column is `DateTime64(3, 'UTC')`, which the driver normally
    returns as a timezone-aware UTC datetime. If a naive datetime is ever
    returned, it is interpreted as UTC rather than the host's local zone;
    otherwise `.timestamp()` would silently shift every watermark by the local
    UTC offset and corrupt the fetch window.
    """
    if value.tzinfo is None:
        value = value.replace(tzinfo=UTC)
    return int(value.timestamp() * 1000)
Trap: the naive-datetime guard is not decoration

A Python datetime without a timezone is called naive. Calling .timestamp() on one makes Python use the machine's local timezone. On a Toronto machine in summer, that is four hours off. Every watermark and fetch window would shift by four hours, silently losing four hours of candles per market. The two-line guard sets the timezone to UTC. The live driver returns aware datetimes, so the guard has not fired, but it protects against a silent failure.

The weakness, stated honestly

The function counts rows sent, and the cycle reports that number as candles_inserted. Each cycle refetches five overlap minutes per market, so about 885 rows in a 177-market cycle may already exist. A real cycle recorded 6,693 candles inserted across 175 markets, about 38 per market. A 15:30 to 16:07 window contains 38 inclusive slots, including the five-minute overlap. This is a write count, not a count of database growth.

Connecting, and what counts as "not ready"

wait_for_clickhouse

Input: connection and backoff settings. Output: a connected client and server version, or an exception. Role: lets the container start before the database is ready.

Network failures such as "connection refused", "name or service not known", and "temporary failure in name resolution" mean "not ready yet". The function retries them forever, doubling the delay from 2 seconds up to 60, with up to one second of random jitter. A wrong password or missing grant becomes ClickHouseConfigurationError and is raised immediately because waiting will not fix it.

Trap: the classification is done by reading text

_looks_like_dependency_not_ready lowercases the exception message and searches for known fragments. If the driver or HTTP library changes its wording, a temporary failure may look like a configuration error and stop the service. This is fragile because the failure occurs below the database protocol, where no error code is available.

Why the client connects to no database in particular

connect_clickhouse omits the database argument on purpose. Statements use full names such as hyperliquid.candles_1m. A user who can access one database but not the server default can still connect. If CREATE DATABASE lacks permission, _ensure_database catches ClickHouse error code 497 and continues.

10Finding and repairing holes

A gap is one or more missing minutes between two stored candles for one market. Structured Query Language (SQL) finds gaps with a window function, which compares each row with the previous row in that market.

SELECT
    symbol,
    prev_open AS gap_after,
    open_time AS gap_before,
    (toUnixTimestamp64Milli(open_time)
      - toUnixTimestamp64Milli(prev_open)) / 60000 - 1 AS missing_minutes
FROM
(
    SELECT
        symbol,
        open_time,
        lagInFrame(open_time) OVER
            (PARTITION BY symbol ORDER BY open_time) AS prev_open
    FROM hyperliquid.candles_1m FINAL
    WHERE open_time >= toDateTime64(1786102260.0, 3, 'UTC')
)
WHERE prev_open != toDateTime64(0, 3)
  AND (toUnixTimestamp64Milli(open_time)
       - toUnixTimestamp64Milli(prev_open)) > 60000
ORDER BY symbol, gap_after
Reading this SQL

lagInFrame(open_time) OVER (PARTITION BY symbol ORDER BY open_time) sorts each market by time and gives every row the previous opening time. PARTITION BY symbol prevents a comparison between two markets. The outer WHERE keeps rows more than one minute after their predecessor: those are the gaps.

The formula

$$g \;=\; \frac{t_{\text{before}} - t_{\text{after}}}{\Delta} \;-\; 1$$

$t_{\text{after}}$ is the opening time immediately before the gap, in gap_after. $t_{\text{before}}$ is the opening time immediately after the gap, in gap_before. $\Delta$ is 60,000 milliseconds. $g$ counts missing minutes strictly between them. The minus one accounts for the two stored endpoints: candles ten minutes apart have nine missing minutes.

Trap: the column names read backwards

gap_after is the earlier timestamp and gap_before the later one. The names describe the gap: it begins after the first candle and ends before the second. _backfill_recoverable_gaps passes them as start_ms=gap.gap_after_ms, end_ms=gap.gap_before_ms, which is correct.

Why the horizon filter is inside the subquery

WHERE open_time >= toDateTime64(horizon_floor, 3, 'UTC') is inside the window-function query. ClickHouse can then skip whole monthly partitions, so the expensive FINAL read touches only recent ones. The query also returns only gaps the exchange can still serve; requesting a ten-week-old gap would waste request budget.

Zero is the measured result. Phase 3 therefore has nothing to repair on this instance, which is the desired steady state.

The weakness, stated honestly

A detected gap is a candidate, not proof of a collection failure. Hyperliquid does not promise a candle for every minute, especially before a new market's first trade. Refetching the boundary is safe, but a gap may remain and appear in every future report. There is also a blind spot at the horizon edge: the first row inside the filtered window has no previous row, so a gap crossing that boundary is invisible to the recoverable query.

What setup_logging does

Input: a level name such as "INFO" and an optional directory. Output: the main log path and three configured handlers. Role: called once per process. The scheduler passes configure_logging=False to later cycles, so a long-running service keeps one log file instead of creating one every half hour.

The destinations are the console, a dated file, and a second file for errors and worse. Names use YYYY-MM-DD_NNN.log; the sequence increases until an unused name is found, so runs on the same day do not overwrite one another.

14Fixes found while writing this page

Reading and running the code found three defects, which were fixed. The full test suite (37 tests) and ruff check passed after each fix.

1. Log timestamps showed the formatting time, not the event time

logging.Formatter passes the record's creation time to converter and expects calendar fields. The old converter ignored that value and used the clock time when formatting occurred.

Sample data — the bug, demonstrated
in — a record created, then formatted three seconds later 
record.created = 2026-08-10T22:55:04.038Z
out 
old converter: 2026-08-10T22:55:07Z INFO demo event happened here   <- three seconds wrong
new converter: 2026-08-10T22:55:04Z INFO demo event happened here   <- matches the record

In ordinary synchronous logging, the error is under a millisecond. It appears when formatting is delayed by a slow disk, queued handler, or burst of records. The log is the service's main record of what happened, so its timestamps must describe the events.

    # `logging.Formatter` calls its converter with the record's own creation
    # time, so the converter must translate that argument. `time.gmtime` turns
    # the record timestamp into UTC calendar fields, which is what the "Z"
    # suffix in `datefmt` promises.
    formatter.converter = time.gmtime

File: src/hyperliquid_candles/logging_setup.py. The unused time_gmtime helper was removed.

2. The scheduler could crash itself with a negative sleep

The loop checked time.monotonic() < deadline and then computed deadline - time.monotonic(). The clock can pass the deadline between those reads, producing a negative duration. time.sleep then raises ValueError: sleep length must be non-negative. Because this is outside the per-cycle try, it would end run_scheduler and stop the service. The failure is rare but difficult to notice.

            remaining_seconds = deadline - time.monotonic()
            time.sleep(max(0.0, min(1.0, remaining_seconds)))

File: src/hyperliquid_candles/scheduler.py.

3. A ClickHouse connection pool was leaked on every cycle

run_once opened two clients but closed only one. The Hyperliquid client was closed in a finally block; the ClickHouse client created inside wait_for_clickhouse was not. A one-shot command hides the leak because the process exits. The scheduler calls run_once every thirty minutes: 48 abandoned connection pools per day, each retaining sockets for the life of the service.

    finally:
        # Both clients are opened by this function, so this function closes
        # them. The scheduler calls `run_once` on every cycle; leaving the
        # ClickHouse connection pool open would leak one pool of sockets per
        # cycle for the life of the service.
        hyperliquid.close()
        client.close()

Files: src/hyperliquid_candles/app.py and tests/unit/test_app.py, where the stand-in ClickHouse object was updated to record that it closed.

Deliberately not changed

Three apparent defects are either operational issues or design choices: the report failing when system.parts is unreadable (section 12); counting rows sent rather than rows added in candles_inserted; and starting the token bucket full (recorded in notes.md). Changing them would change behaviour rather than fix a coding error.

18If someone points at a line

QuestionAnswer
"Where could future information leak into the data?"Only through the in-progress candle, and last_closed_open_ms excludes it by subtracting one interval. Everything stored is a finished minute. There is no forward-filling, no interpolation, and no derived column
"Why not just page forward by start time?"Because truncation is anchored to the newest end. The live probe in section 8 shows a 6,001-slot request returning 5,217 rows, all 784 dropped slots coming off the old end
"Why is there no watermark table?"It would be a second source of truth that could disagree with the rows. The rows are the state
"What happens if I set poll_interval_sec = 60?"Nothing breaks immediately: a 177-market sweep costs about 3,540 weight, roughly 3.5 minutes at the 1,000 per minute budget. Cycles would then overlap the interval and effectively run back to back. Below the sweep time the service simply never idles
"How long does a cycle take in practice?"Two and a half minutes for 175 markets, from four consecutive real runs recorded in ingestion_runs
"Why Float64 for volume rather than something smaller?"Because the exchange's own values are the product. Narrowing to 32 bits would change stored numbers to save space. The compression codecs shrink the file without touching the values
"Can I trust count() on candles_1m?"Not exactly. 4,965 duplicate keys are currently awaiting merge. Group by (symbol, open_time) and use argMax(col, inserted_at), or use FINAL
"Why does candles_inserted exceed the minutes that elapsed?"It counts rows sent, and each cycle deliberately resends five overlap minutes per market. 6,693 rows across 175 markets is about 38 per market, matching the 38-slot window the status rows record
"What happens if the service is off for four days?"Everything past the 4,999-minute horizon is gone permanently. The quality report would show critical; the configured threshold fires eleven hours before that point
"Why does the gap query use gap_after for the earlier time?"The columns are named relative to the gap, not to each other. The gap begins after the first candle and ends before the second
"Is except Exception not too broad?"In _fetch_store_status it is the point: isolate one market. It is not silent — full traceback to the log, error text to ingestion_symbol_status, and the run status drops to partial
"Which settings does the ingestion path ignore?"All four alert_* thresholds. They only shape the wording of the quality report

19Limitations, stated honestly

History cannot be recovered, only accumulated

This project cannot retrieve a minute older than the exchange's recent window. If the service is down for four days, those four days are gone. The measured 50 days of history exist because the process ran continuously; three markets in the live instance have been frozen since June, and their missing minutes cannot be recovered.

A gap can be a source fact, not a collection failure

Hyperliquid does not guarantee a candle for every minute. Refetching a gap is safe but may not fill it, so the same candidate can appear in every future report. This code cannot distinguish "we missed it" from "it never existed".

The rate budget is a local promise, not a contract

The exchange's 1,200-per-minute ceiling covers everything leaving the internet address, not just this process. The bucket assumes it is the only consumer. Another tool sharing the address can overspend without the bucket knowing.

Nearly one minute in five has no trades

2,380,174 of 13,002,252 stored rows have trades = 0. These are valid exchange output with a carried-forward price. Volatility, return, or liquidity calculations that treat them as ordinary observations will understate movement. The collector stores them and exposes the count through the trades column.

Volume is not comparable across markets

The volume column measures the underlying asset, not dollars. One unit of BTC and one unit of DOGE have very different values. A rough dollar figure is $\text{notional} = v \times c$, where $v$ is volume and $c$ is the close. From the sample: $1.29563 \times 63{,}976 = 82{,}889$ USD Coin (USDC) for one minute. The table does not store this value; callers must calculate it.

Failure counting is pessimistic and one-dimensional

A market that succeeds in phase 2 but fails during gap repair is counted as failed, so symbols_ok can understate what was collected. A run that fails before the metadata write creates no ingestion_runs row. That missing row is itself the signal, but it is easy to miss.

The horizon setting and the alert thresholds are not linked

rest_horizon_candles = 5000 and alert_critical_min = 4320 are related by arithmetic, not by code. Changing one without the other can move the alarm to the wrong side of the recovery limit.

Running it yourself

Run uv sync, then cp .env.example .env and fill in the ClickHouse values. uv run hyperliquid-candles-run-once performs one cycle, uv run hyperliquid-candles starts the service, and uv run hyperliquid-candles-quality prints the report. In this environment, the tests needed uv run --with typing_extensions pytest because the installed anyio version imports typing_extensions unconditionally while declaring it only for older Python versions. That is a dependency packaging quirk, not a project fault.
