Collecting Hyperliquid minute candles: reading the code

What the service does, how the pieces fit together, and the handful of ideas you have to hold in your head to read any file in it.

How to use this

Sections follow the order in which one ingestion cycle runs. Every code snippet is copied unchanged from the files under src/hyperliquid_candles/. Every number in a grey Sample data box was printed by actually running the code on 10 August 2026 against the live Hyperliquid public endpoint and the project's own ClickHouse server. Coloured boxes flag design choices, traps, and honest weaknesses.

The process in plain English

Hyperliquid is a crypto derivatives exchange. Its public web interface will hand you the last few thousand one-minute price bars for each market, but nothing older. This service keeps a permanent copy: every half hour it wakes up, asks the database "what is the newest bar I already have for each market?", asks Hyperliquid for everything since then, and writes the result back. Because it does that forever, the database slowly accumulates history the exchange itself will no longer serve. Nothing is stored in memory between cycles, so the service can be killed and restarted at any moment without losing its place.

Rounded boxes are functions, named exactly as they are in the code. Cylinders are stored data. Arrows point the way data moves. 01The goal, and the one rule everything follows

A candle (also called a bar) summarises all trading in one time slot with six numbers: the first traded price (open), the highest and lowest prices (high, low), the last price (close), how much was traded (volume), and how many trades happened. This project collects one-minute candles for Hyperliquid's perpetual markets. A perpetual is a derivative contract that tracks an asset's price and never expires; traders call them "perps".

Hyperliquid's documentation promises only the most recent 5,000 candles per market through its public request-and-response interface. At one minute each, that is roughly three and a half days. Anything older is simply gone from that interface. So the project's one job is: stay online, and keep copying the recent window into a database before it scrolls away.

The one rule: the database is the only memory

The service holds no state between cycles — no watermark file, no cache, no in-memory bookmark. At the start of every cycle it asks ClickHouse SELECT symbol, max(open_time) ... GROUP BY symbol and rebuilds its plan from that answer. Kill the process mid-write and the next cycle simply sees a slightly older maximum and refetches. This is why there is no watermark table: a second copy of "where I got to" could disagree with the rows themselves, and then you would have to decide which one is right.

Vocabulary used throughout this page

ClickHouse is the database, a column-oriented store built for large analytical tables. It is not installed or managed by this project; it must already exist. Watermark means the newest open_time already stored for one symbol. REST means the ordinary request-and-response web interface (as opposed to a streaming connection). Horizon means the oldest candle Hyperliquid will still serve. Idempotent means an operation you can repeat without changing the outcome: inserting the same candle twice leaves the same single candle.

    # Precedence: the `.env` file is the authoritative source for ClickHouse
    # connection values; the process environment only fills keys the file omits.
    # This is deliberate. On a host whose shell already exports these variables,
    # a value can be silently corrupted (for example a password containing `$`
    # mangled by shell expansion). Letting the file win keeps the documented
    # `.env` as the single source of truth and makes loading deterministic.
    file_env = dotenv_values(resolved_env_path) if resolved_env_path.exists() else {}
    merged_env: dict[str, str | None] = {
        key: os.environ[key] for key in _CLICKHOUSE_ENV_KEYS if key in os.environ
    }
    merged_env.update(file_env)
Why the file beats the environment

This is backwards from the usual convention, where an exported shell variable overrides a file. The reason is given in the comment: a password containing a dollar sign gets eaten by shell expansion, and the resulting failure looks like a wrong password rather than a mangled one. Making the file authoritative means "what is in .env is what the service uses", with no invisible third party.

Trap: the critical threshold is not arbitrary

alert_critical_min = 4320 is 72 hours. The recoverable horizon is 4,999 minutes, or 83.3 hours. The alarm is set to fire about eleven hours before the oldest missing minute becomes permanently unrecoverable. If you raise rest_horizon_candles or lower it, this threshold should move with it; nothing in the code enforces that relationship.

Where the project root comes from

PROJECT_ROOT = Path(__file__).resolve().parents[2] in config.py walks up from src/hyperliquid_candles/config.py to the repository root, so commands work from any working directory. The environment variable HL_DATA_DIR relocates writable files (logs, and an optional overriding config.toml); the Docker image sets it to /data. It is read from the process environment, not from .env, because the loader must know where writable files live before it can read any file.

run_scheduler — sleep, but stay interruptible

    while not stop_requested:
        try:
            cycle_callback()
        except Exception:
            # A single cycle failure (network blip, transient ClickHouse error)
            # must not kill the long-running loop. Log it and continue to the
            # next scheduled tick; ClickHouse rows remain the source of truth, so
            # the next cycle recovers any missed window from stored watermarks.
            LOGGER.exception("Ingestion cycle failed; continuing to next cycle")
        jitter_seconds = random.uniform(
            0, min(30, settings.ingestion.poll_interval_sec / 10)
        )
        sleep_seconds = settings.ingestion.poll_interval_sec + jitter_seconds
        LOGGER.info("Sleeping %.1f seconds before next ingestion cycle", sleep_seconds)

        deadline = time.monotonic() + sleep_seconds
        while not stop_requested and time.monotonic() < deadline:
            # The clock advances between the loop test and this line, so the
            # remaining time can already be negative. `time.sleep` raises on a
            # negative argument, which would kill the service loop, so clamp it.
            remaining_seconds = deadline - time.monotonic()
            time.sleep(max(0.0, min(1.0, remaining_seconds)))
In plain words

Do the work, write down anything that went wrong, then nap in one-second pieces so a shutdown signal is noticed within a second rather than half an hour later.

What it does

Input: the settings, and a function to call each cycle. Output: nothing; it returns only when a stop signal arrives. Role: the outer shell of the long-running service.

Why the sleep is chopped into one-second slices

signal.signal hands the handler a flag, but a single time.sleep(1800) would not check that flag until it finished. Slicing the wait means docker compose down or Ctrl-C is honoured in about a second, and the container is not killed by force. time.monotonic() is used rather than wall clock time so that a system clock adjustment cannot make the sleep last forever.

Why the jitter

random.uniform(0, min(30, interval/10)) adds up to thirty seconds of random delay. If several copies of this service (or several services on one machine) restarted at the same instant, they would otherwise stay in lockstep and hit the exchange in bursts forever. The jitter breaks that alignment. The hard cap of thirty seconds is written inline rather than being a setting.

04Choosing which markets to collect

def active_perp_symbols(meta_response: dict[str, Any]) -> tuple[str, ...]:
    """Return active perpetual symbols from a Hyperliquid `meta` response.

    Hyperliquid names perpetual markets in `universe`. Delisting flags are not
    always present, so the parser treats missing flags as active.
    """
    raw_universe = meta_response.get("universe", [])
    if not isinstance(raw_universe, list):
        raise ValueError("Hyperliquid meta response has no universe list")

    symbols: list[str] = []
    for item in raw_universe:
        if not isinstance(item, dict):
            continue
        symbol = item.get("name")
        is_delisted = bool(item.get("isDelisted", False))
        if isinstance(symbol, str) and symbol and not is_delisted:
            symbols.append(symbol)

    return tuple(sorted(set(symbols)))
What it does

Input: the JSON object Hyperliquid returns for a meta request. Output: a sorted tuple of market names with no duplicates. Role: decides the work list for the whole cycle.

The database holds 180 symbols but only 177 are active today. The extra three are markets that were delisted after their rows were collected; their history stays, but the service no longer asks for updates on them.

Why sorting matters more than it looks

The exchange returns markets in its own order, starting with BTC. Sorting makes each cycle deterministic: the same universe produces the same work order, so log files from two cycles line up and can be compared line by line. set() before sorted() also means a repeated name in the response cannot cause the same market to be fetched twice.

Trap: a missing flag means active

item.get("isDelisted", False) treats an absent flag as "still trading". That is the safe default here — collecting a market you did not need costs one small request, whereas silently dropping a live market loses data you can never recover. But it does mean that if Hyperliquid ever renames the field, every delisted market quietly comes back into the work list.

Allowlist mode fails loudly

select_symbols in allowlist mode raises ValueError if any requested name is not currently active. A typo in config.toml stops the whole cycle rather than silently collecting three markets when you asked for four. Verified live: select_symbols(meta, "allowlist", ("BTC", "ETH")) returned ('BTC', 'ETH').

05Time arithmetic

Every timestamp inside the service is an integer: Unix epoch milliseconds, meaning the number of milliseconds since midnight UTC on 1 January 1970. Conversion to a Python datetime happens only at the ClickHouse boundary. Integers cannot drift, cannot carry a surprise timezone, and compare exactly.

last_closed_open_ms — never store a bar that is still forming

def last_closed_open_ms(now_ms: int | None = None) -> int:
    """Return the open time of the latest fully closed 1-minute candle."""
    effective_now_ms = now_ms
    if effective_now_ms is None:
        effective_now_ms = int(datetime.now(tz=UTC).timestamp() * 1000)
    current_minute_open_ms = effective_now_ms // INTERVAL_MS * INTERVAL_MS
    return current_minute_open_ms - INTERVAL_MS
The formula

$$t_{\text{last}} \;=\; \left\lfloor \frac{t_{\text{now}}}{\Delta} \right\rfloor \Delta \;-\; \Delta$$

$t_{\text{now}}$ is the current time in Unix epoch milliseconds. $\Delta = 60{,}000$ is one minute in milliseconds, the constant INTERVAL_MS. The floor bars $\lfloor \cdot \rfloor$ mean "round down to a whole number", so $\lfloor t_{\text{now}}/\Delta \rfloor \Delta$ is the start of the minute we are currently inside. Subtracting one more $\Delta$ steps back to the minute that has already finished. $t_{\text{last}}$ is the newest candle open time the service will ever request.

Trap: this single line is what keeps the data honest

At 22:51:47 the 22:51 candle exists at the exchange, but its high, low, close and volume are still changing. If the service stored it, the database would contain a bar whose numbers depend on the moment you happened to ask, and a later research query would see a "22:51 close" that was never a real closing price. Anyone testing a trading rule on that data would be reading a price that was not knowable at the time — the classic look-ahead mistake. Subtracting one interval removes the possibility entirely: only finished minutes are ever written.

earliest_open_ms_for_candle_count — the fencepost

    if candle_count <= 0:

The formula

$$t_{\text{floor}} \;=\; t_{\text{last}} \;-\; (N-1)\,\Delta$$

$N$ is rest_horizon_candles, the number of candle slots in the window, counting both ends. $t_{\text{floor}}$ is the open time of the oldest one. The $N-1$ is the fencepost correction: five fence posts have four gaps between them, and five candles have four intervals between their opening times.

build_incremental_work_items — one window per stored market

    for symbol in symbols:

The formula

$$s \;=\; \max\!\bigl(w - k\Delta,\; t_{\text{floor}}\bigr), \qquad e \;=\; t_{\text{last}}$$

$w$ is the watermark, the newest open time already stored for that market. $k$ is overlap_candles (5 by default), so $w - k\Delta$ deliberately steps back five minutes into data already held. $t_{\text{floor}}$ is the horizon from the previous formula, so the $\max$ refuses to ask for anything the exchange cannot serve. $[s, e]$ is the inclusive window this cycle will request for that market.

Why refetch five minutes you already have

Two reasons. The exchange can revise a candle briefly after it closes, and a cycle can die between fetching and inserting. Re-requesting the last five minutes covers both, and costs nothing because the database key makes repeats harmless. The price is a small number of duplicate rows waiting to be merged: measured at 4,965 out of 13 million, or 0.04 per cent.

06Talking to Hyperliquid

candle_request_weight — guessing the bill before you order

Hyperliquid does not count requests; it counts weight, a cost number attached to each call. The published ceiling is 1,200 weight per minute per internet address. A candleSnapshot call costs a base of 20 plus one more for every 60 candles it returns.

    requested_slots = (end_ms - start_ms) // INTERVAL_MS + 1
    return BASE_INFO_WEIGHT + requested_slots // ITEM_WEIGHT_BLOCK
The formula

$$n \;=\; \frac{e-s}{\Delta} + 1, \qquad W \;=\; 20 \;+\; \left\lfloor \frac{n}{60} \right\rfloor$$

$s$ and $e$ are the requested window bounds in milliseconds, $n$ is the number of minute slots asked for, and $W$ is the estimated weight. The constant 20 is BASE_INFO_WEIGHT and the 60 is ITEM_WEIGHT_BLOCK. The exchange charges on candles returned, which is never more than the number requested, so this estimate always errs on the expensive side.

TokenBucket — a tap that refills at a fixed rate

    def wait_for(self, weight: float) -> None:
        """Block until at least `weight` request tokens are available."""
        if weight <= 0:
            raise ValueError("weight must be positive")

        while True:
            self._refill()
            if self._tokens >= weight:
                self._tokens -= weight
                return

            missing_tokens = weight - self._tokens
            tokens_per_second = self.tokens_per_minute / 60.0
            time.sleep(missing_tokens / tokens_per_second)
In plain words

Think of a bucket that fills with coins at a steady rate. Every request must pay coins before it is sent. If the bucket is short, the caller waits exactly long enough for the missing coins to drip in.

The formula

$$T \leftarrow \min\!\left(C,\; T + (\tau - \tau_{\text{prev}})\frac{B}{60}\right), \qquad \text{wait} \;=\; \frac{W - T}{B/60}$$

$T$ is the tokens currently in the bucket, $C$ its capacity (equal to $B$ unless set otherwise), $B$ is weight_budget_per_min, $\tau$ is the current reading of a steadily increasing clock in seconds and $\tau_{\text{prev}}$ the previous reading, and $W$ is the weight this request needs. The first expression is the refill: time elapsed times the per-second rate, capped at capacity. The second is how long to sleep when the bucket is short.

Why the weight is reserved before sending, not after

The client calls rate_limiter.wait_for(request_weight) inside the retry wrapper, before the HTTP call. Charging afterwards, once the true response size is known, would let a cold start fire dozens of requests instantly and only then discover it had overspent. Reserving first means the very first burst is already paced.

The weakness, stated honestly

The bucket starts full. Its capacity defaults to one full minute of budget, so in the first minute of a fresh process it can spend capacity plus refill: 1,000 + 1,000 = 2,000 weight, against an exchange ceiling of 1,200. The retry logic absorbs the resulting refusals, but the guarantee is not tight. The project's own notes.md records this and suggests capping capacity so that capacity plus budget stays under 1,200. It has not been done.

_post_info_with_retry — what counts as worth retrying

        @retry(
            retry=retry_if_exception_type((httpx.HTTPError, RuntimeError)),
            stop=stop_after_attempt(self.max_retries),
            wait=wait_exponential_jitter(initial=1, max=30),
            reraise=True,
        )
        def _send() -> Any:
            # Reserve the full estimated weight before each attempt. Charging
            # response-item weight afterwards permits an initial burst that can
            # exceed the configured per-minute budget.
            self.rate_limiter.wait_for(request_weight)
            response = self._client.post(self.base_url, json=payload)
            if response.status_code == 429 or response.status_code >= 500:
                raise RuntimeError(
                    f"Transient Hyperliquid status {response.status_code}: {response.text[:200]}"
                )
            response.raise_for_status()
            return response.json()
What it does

Input: a JSON request body and an estimated weight. Output: the decoded JSON response. Role: the single door through which every exchange call passes.

Status 429 means "too many requests" and 500 and above mean "the server broke". Both are turned into a RuntimeError, which the retry decorator recognises. Anything else — a 400 for a malformed request, a 404 — goes through raise_for_status() as an httpx.HTTPStatusError, and although that is a subclass of httpx.HTTPError and therefore also retried, no amount of retrying will fix it, so it eventually surfaces.

Trap: the weight is paid on every attempt

wait_for sits inside _send, not outside it. A request that is refused four times pays four times. That is the correct behaviour — the exchange charges for refused calls too — but it means a struggling connection burns budget that healthy markets then have to wait for.

      "c": "63976.0", ...}
out 
ValueError: Candle high is below

The failure is raised per market inside _fetch_store_status, so one malformed market is recorded as failed and the other 176 still get written.

Why check things that "cannot" be wrong

The high can never be below the open in a correct bar, so these checks look like paranoia. Their real job is to catch a change at the exchange — a renamed field, a new interval string, a units change — on the day it happens, as a loud per-market failure, rather than months later as a silently corrupted table that every downstream study has already used.

Trap: trades = 0 is normal, not missing data

Hyperliquid emits a candle for a minute in which nothing traded, carrying the previous price forward so that open, high, low and close are all equal and volume is zero. The parser accepts these, correctly. Measured on the live table: 2,380,174 of 13,002,252 rows, or 18.3 per cent, have zero trades. Any volatility or liquidity study that treats those rows as real price observations will understate movement. This is a property of the data, not a bug in the collector.

dedupe_by_symbol_open_time

Input: candles from several pages, possibly overlapping. Output: one candle per (symbol, open_time_ms) pair, sorted. Role: stops the same minute being sent to the database twice within a single request. Verified: six rows in, three rows out. The dictionary assignment keeps the last one seen, and since all copies come from the same source in the same cycle, which one wins does not matter.

08Paging backwards

This is the single idea that makes the project work, and it is the opposite of what most people write first.

Why forward paging cannot work here

Ask Hyperliquid for a window wider than it can serve, and it does not return the oldest part and stop. It returns the part nearest the end of your window and silently drops the oldest overflow. So if you ask for "everything from ten weeks ago until now" and then try to advance your start time page by page, every page returns the same recent chunk near the end and you never move. The fix is to walk the end of the window backwards instead, peeling off the next-oldest chunk each time.

Sample data — the truncation, probed live
in — one raw candleSnapshot request for BTC 
startTime  2026-08-06T18:50:00Z
endTime    2026-08-10T22:50:00Z
slots requested   6,001
out — the response 
rows returned     5,217
oldest returned   2026-08-07T07:54:00Z   <- 784 slots later than asked for
newest returned   2026-08-10T22:50:00Z   <- exactly the end requested

784 slots were dropped, and every one of them came off the OLD end.

Two things worth noticing. The endpoint returned 5,217 rows, more than the documented 5,000 — the real horizon is a little more generous than the promise, which is why the code treats 5,000 as a conservative setting rather than a hard fact. And the loss is entirely at the old end, which is the behaviour the whole module is built around.

    fetched_rows: list[Candle] = []
    cursor_end_ms = end_ms

    while cursor_end_ms >= start_ms:
        page = source.fetch_candles(
            symbol=symbol, start_ms=start_ms, end_ms=cursor_end_ms
        )
        if not page:
            break

        fetched_rows.extend(page)
        oldest_open_ms = min(candle.open_time_ms for candle in page)

        # The page already reaches the requested start, so the window is covered.
        if oldest_open_ms <= start_ms:
            break

        # Step the cursor to just before the oldest candle we just received so
        # the next request peels off the next-older chunk.
        next_cursor_end_ms = oldest_open_ms - interval_ms

        # Defensive guard: if the cursor did not move backward, the API is not
        # honouring endTime as expected. Stop rather than loop forever.
        if next_cursor_end_ms >= cursor_end_ms:
            break

        cursor_end_ms = next_cursor_end_ms

    return dedupe_by_symbol_open_time(fetched_rows)
In plain words

Ask for the window. Look at the oldest bar you got back. Ask again, this time ending one minute before that. Repeat until you either reach the start you wanted or the exchange stops giving you anything new.

What it does

Input: a market name, an inclusive window in milliseconds, and any object with a fetch_candles method. Output: every candle in that window the exchange still exposes, deduplicated and sorted. Possibly an empty list. Role: the one fetch primitive. Initial backfill, incremental catch-up and gap repair all go through it, so there is exactly one place where pagination can be right or wrong.

Why termination depends on the cursor, never on page size

A tempting stopping rule is "stop when a page comes back smaller than the maximum". That breaks the moment the exchange changes its page size, and it is wrong for a market that genuinely has fewer bars. This loop stops on three conditions instead, all of them about progress: the page was empty, the page reached the requested start, or the cursor failed to move backwards. The third is the one that matters — if the endpoint ever ignored endTime, every page would be identical and a size-based rule would spin forever.

Trap: the loop can return fewer rows than asked for, silently

When the window reaches past the horizon, the loop simply stops and returns what exists. There is no error and no warning. That is intentional — a ten-week-old gap is not recoverable and complaining about it every cycle would be noise — but it means "fetched 40 rows" never proves "40 rows existed". The per-market status row records requested_start and effective_start separately so the difference stays visible afterwards.

09Writing and reading ClickHouse

The table, and why re-inserting is safe

CREATE TABLE IF NOT EXISTS {database}.candles_1m
(
    symbol      LowCardinality(String),
    open_time   DateTime64(3, 'UTC')  CODEC(DoubleDelta, ZSTD(12)),
    close_time  DateTime64(3, 'UTC')  CODEC(DoubleDelta, ZSTD(12)),
    open        Float64               CODEC(Delta, ZSTD(12)),
    high        Float64               CODEC(Delta, ZSTD(12)),
    low         Float64               CODEC(Delta, ZSTD(12)),
    close       Float64               CODEC(Delta, ZSTD(12)),
    volume      Float64               CODEC(ZSTD(12)),
    trades      UInt32                CODEC(T64, ZSTD(12)),
    inserted_at DateTime64(3, 'UTC')  DEFAULT now64(3) CODEC(DoubleDelta, ZSTD(12))
)
ENGINE = ReplacingMergeTree(inserted_at)
PARTITION BY toYYYYMM(open_time)
ORDER BY (symbol, open_time)
SETTINGS index_granularity = 8192
Reading this DDL

DDL stands for data definition language — the SQL that creates tables. ReplacingMergeTree(inserted_at) is a ClickHouse table engine that, when two rows share the sorting key, eventually keeps the one with the larger inserted_at. The sorting key here is (symbol, open_time), so one market-minute resolves to one row. CODEC chooses how a column is compressed before it is written. Delta stores each value as the difference from the previous one; DoubleDelta stores the difference of the differences, which is nearly free for evenly spaced timestamps; T64 packs small integers together; ZSTD(12) is general-purpose compression at a high setting. LowCardinality(String) stores repeated strings as small numbers pointing into a dictionary — 180 market names repeated 13 million times compress to almost nothing.

Why volume alone gets no delta encoding

Prices move gradually minute to minute, so the difference between consecutive values is small and compresses well. Traded volume does not: it jumps between near zero and large values with no relationship to its neighbour, so a difference is as large as the original number and delta encoding makes the file bigger. The project measured this and recorded the result in COMPRESSION_BENCHMARK.md. Note that the compression choices are all lossless — the alternative of shrinking volume to a 32-bit float was rejected because it would quietly change the stored numbers.

Trap: "eventually" is doing real work in that sentence

ReplacingMergeTree removes duplicates during background merges, on ClickHouse's schedule, not at insert time. Until then both rows are visible to a plain SELECT. On the live table right now that is 4,965 duplicate keys. Any research query must collapse them itself, with FINAL or with argMax(column, inserted_at) grouped by (symbol, open_time). A naive count() or avg() over this table is slightly wrong.

Reading the watermarks

def datetime_to_ms(value: datetime) -> int:
    """Convert a ClickHouse datetime value to Unix epoch milliseconds.

    The `candles_1m` column is `DateTime64(3, 'UTC')`, which the driver normally
    returns as a timezone-aware UTC datetime. If a naive datetime is ever
    returned, it is interpreted as UTC rather than the host's local zone;
    otherwise `.timestamp()` would silently shift every watermark by the local
    UTC offset and corrupt the fetch window.
    """
    if value.tzinfo is None:
        value = value.replace(tzinfo=UTC)
    return int(value.timestamp() * 1000)
Trap: the naive-datetime guard is not decoration

A Python datetime with no timezone attached is called naive. Calling .timestamp() on one makes Python assume the machine's local timezone. On a Toronto machine in summer that is four hours off. Every watermark would move four hours, every fetch window would start four hours late, and the service would quietly lose four hours of candles per market with no error anywhere. The two-line guard converts the assumption to UTC instead. Confirmed live: the driver does return aware datetimes, so the guard never fires — but it costs nothing and the failure it prevents is invisible.

The weakness, stated honestly

The function counts rows sent, and the cycle reports that number as candles_inserted. Because every cycle deliberately refetches five overlap minutes per market, roughly 885 of the rows in a 177-market cycle are already present. The live table bears this out: a real cycle recorded 6,693 candles inserted across 175 markets, about 38 per market, and the per-market rows show why — a window from 15:30 to 16:07 is 38 inclusive minute slots, of which five are the deliberate overlap. The figure is a write count, not a growth count.

Connecting, and what counts as "not ready"

wait_for_clickhouse

Input: connection settings and the backoff settings. Output: a connected client plus the server version, or an exception. Role: lets the container start before the database does.

The distinction it draws is the interesting part. Network-shaped failures — "connection refused", "name or service not known", "temporary failure in name resolution" — are treated as "not ready yet" and retried forever with a doubling delay from 2 seconds up to 60, plus up to one second of random jitter. Anything else, such as a wrong password or a missing grant, is wrapped in ClickHouseConfigurationError and raised immediately, because no amount of waiting will fix it.

Trap: the classification is done by reading text

_looks_like_dependency_not_ready lowercases the exception message and looks for known fragments. If the driver or the underlying HTTP library rewords its errors, a genuinely transient failure would be reclassified as a configuration error and the service would stop instead of waiting. This is fragile by nature; there is no error code to check because the failure happens below the database protocol.

Why the client connects to no database in particular

connect_clickhouse deliberately omits the database argument. Every statement in the project writes the name out in full, as hyperliquid.candles_1m. That way a user who has rights on one database but cannot see the server default still connects cleanly, and CREATE DATABASE is attempted but forgiven if the grant is missing — _ensure_database catches ClickHouse error code 497 and carries on.

10Finding and repairing holes

A gap is one or more absent minutes between two stored candles for the same market. The detection is done in SQL, using a window function that looks at the previous row within each market.

SELECT
    symbol,
    prev_open AS gap_after,
    open_time AS gap_before,
    (toUnixTimestamp64Milli(open_time)
      - toUnixTimestamp64Milli(prev_open)) / 60000 - 1 AS missing_minutes
FROM
(
    SELECT
        symbol,
        open_time,
        lagInFrame(open_time) OVER
            (PARTITION BY symbol ORDER BY open_time) AS prev_open
    FROM hyperliquid.candles_1m FINAL
    WHERE open_time >= toDateTime64(1786102260.0, 3, 'UTC')
)
WHERE prev_open != toDateTime64(0, 3)
  AND (toUnixTimestamp64Milli(open_time)
       - toUnixTimestamp64Milli(prev_open)) > 60000
ORDER BY symbol, gap_after
Reading this SQL

lagInFrame(open_time) OVER (PARTITION BY symbol ORDER BY open_time) means: sort each market's rows by time, and for every row give me the previous row's open time. PARTITION BY symbol stops one market's last row being compared with the next market's first. The outer WHERE keeps only rows whose neighbour is more than one minute away — those are the holes.

The formula

$$g \;=\; \frac{t_{\text{before}} - t_{\text{after}}}{\Delta} \;-\; 1$$

$t_{\text{after}}$ is the open time of the stored candle immediately before the hole (the column named gap_after) and $t_{\text{before}}$ the stored candle immediately after it (the column named gap_before). $\Delta$ is again 60,000 milliseconds. $g$ is the count of missing minutes strictly between the two. The minus one is the same fencepost correction as before: two candles ten minutes apart have nine minutes missing between them.

Trap: the column names read backwards

gap_after is the earlier timestamp and gap_before is the later one. They are named for the gap, not for each other: the gap comes after the first candle and before the second. In _backfill_recoverable_gaps they are passed as start_ms=gap.gap_after_ms, end_ms=gap.gap_before_ms, which is correct, but the line reads like a mistake at first glance. Anyone editing this should check the ordering before "fixing" it.

Why the horizon filter is inside the subquery

WHERE open_time >= toDateTime64(horizon_floor, 3, 'UTC') sits with the window function, not outside it. That lets ClickHouse skip whole monthly partitions, so the expensive FINAL read touches only the recent ones. It also means the query returns only gaps the exchange could still serve — asking to refetch a gap from ten weeks ago would spend request budget on data that no longer exists anywhere.

The weakness, stated honestly

A detected gap is a candidate, not proof of a collection failure. Hyperliquid does not promise a candle for every minute of every market's life, particularly for a newly listed market before its first trade. Refetching the boundary window is harmless, but a gap can survive a successful repair and reappear in every future report. The module docstring says this plainly. There is also a blind spot at the horizon edge: the first row inside the filtered window has no previous row, so a gap that straddles the boundary is invisible to the recoverable query.

No failures gives success. Every market failing gives failed. Anything between gives partial. A market that succeeds in phase 2 but fails during gap repair counts as failed — the count is deliberately pessimistic.

Input: a level name such as "INFO", and an optional directory. Output: the path of the main log file, and three configured handlers. Role: called once per process. The scheduler passes configure_logging=False to each cycle so that a service running for months writes one log file, not one per half hour.

Three destinations: the console, a dated file, and a second file that receives only errors and worse. The naming is YYYY-MM-DD_NNN.log with the sequence number incrementing until an unused name is found, so two runs on the same day never overwrite each other.

14Fixes applied while writing this page

Three defects were found by reading, confirmed by running, and fixed. The full test suite (37 tests) and ruff check pass after each.

1. Log timestamps showed the formatting time, not the event time

logging.Formatter calls its converter with the record's own creation time and expects calendar fields back. The old converter ignored that argument entirely and returned the clock reading at the moment of formatting.

Sample data — the bug, demonstrated
in — a record created, then formatted three seconds later 
record.created = 2026-08-10T22:55:04.038Z
out 
old converter: 2026-08-10T22:55:07Z INFO demo event happened here   <- three seconds wrong
new converter: 2026-08-10T22:55:04Z INFO demo event happened here   <- matches the record

In ordinary synchronous logging the error is under a millisecond, which is why it was never noticed. It becomes visible whenever formatting is delayed — a slow disk, a queued handler, or a burst of records flushed together. Since a log file is the only forensic record this service leaves behind, its timestamps should mean what they say.

    # `logging.Formatter` calls its converter with the record's own creation
    # time, so the converter must translate that argument. `time.gmtime` turns
    # the record timestamp into UTC calendar fields, which is what the "Z"
    # suffix in `datefmt` promises.
    formatter.converter = time.gmtime

File: src/hyperliquid_candles/logging_setup.py. The now-unused time_gmtime helper was removed.

2. The scheduler could crash itself with a negative sleep

The inner wait loop tested time.monotonic() < deadline and then, on the next line, computed deadline - time.monotonic(). The clock advances between those two moments. When the deadline is within microseconds, the second reading can already be past it, giving a negative duration — and time.sleep raises ValueError: sleep length must be non-negative. That exception is outside the per-cycle try, so it would propagate out of run_scheduler and end the service. Rare, but the failure mode is "the collector stops and nobody notices for days".

            remaining_seconds = deadline - time.monotonic()
            time.sleep(max(0.0, min(1.0, remaining_seconds)))

File: src/hyperliquid_candles/scheduler.py.

3. A ClickHouse connection pool was leaked on every cycle

run_once opened two clients and closed one. The Hyperliquid client was closed in a finally block; the ClickHouse client, created inside wait_for_clickhouse, never was. A one-shot command does not care, because the process exits. The scheduler calls run_once every thirty minutes forever: 48 abandoned connection pools per day, each holding its own sockets, for the life of the service.

    finally:
        # Both clients are opened by this function, so this function closes
        # them. The scheduler calls `run_once` on every cycle; leaving the
        # ClickHouse connection pool open would leak one pool of sockets per
        # cycle for the life of the service.
        hyperliquid.close()
        client.close()

Files: src/hyperliquid_candles/app.py, and tests/unit/test_app.py where the stand-in ClickHouse object was extended to record that it was closed.

Deliberately not changed

Three things that look like defects but are not, or are design decisions rather than bugs: the report failing entirely when system.parts is unreadable (an operational grant problem, described in section 12); candles_inserted counting rows sent rather than rows added (documented in the writer's docstring); and the token bucket starting full (recorded as a known trade-off in notes.md). Changing any of these alters behaviour rather than fixing a mistake.

18If someone points at a line

QuestionAnswer
"Where could future information leak into the data?"Only through the in-progress candle, and last_closed_open_ms excludes it by subtracting one interval. Everything stored is a finished minute. There is no forward-filling, no interpolation, and no derived column
"Why not just page forward by start time?"Because truncation is anchored to the newest end. The live probe in section 8 shows a 6,001-slot request returning 5,217 rows, all 784 dropped slots coming off the old end
"Why is there no watermark table?"It would be a second source of truth that could disagree with the rows. The rows are the state
"What happens if I set poll_interval_sec = 60?"Nothing breaks immediately: a 177-market sweep costs about 3,540 weight, roughly 3.5 minutes at the 1,000 per minute budget. Cycles would then overlap the interval and effectively run back to back. Below the sweep time the service simply never idles
"How long does a cycle take in practice?"Two and a half minutes for 175 markets, from four consecutive real runs recorded in ingestion_runs
"Why Float64 for volume rather than something smaller?"Because the exchange's own values are the product. Narrowing to 32 bits would change stored numbers to save space. The compression codecs shrink the file without touching the values
"Can I trust count() on candles_1m?"Not exactly. 4,965 duplicate keys are currently awaiting merge. Group by (symbol, open_time) and use argMax(col, inserted_at), or use FINAL
"Why does candles_inserted exceed the minutes that elapsed?"It counts rows sent, and each cycle deliberately resends five overlap minutes per market. 6,693 rows across 175 markets is about 38 per market, matching the 38-slot window the status rows record
"What happens if the service is off for four days?"Everything past the 4,999-minute horizon is gone permanently. The quality report would show critical; the configured threshold fires eleven hours before that point
"Why does the gap query use gap_after for the earlier time?"The columns are named relative to the gap, not to each other. The gap begins after the first candle and ends before the second
"Is except Exception not too broad?"In _fetch_store_status it is the point: isolate one market. It is not silent — full traceback to the log, error text to ingestion_symbol_status, and the run status drops to partial
"Which settings does the ingestion path ignore?"All four alert_* thresholds. They only shape the wording of the quality report

19Limitations, stated honestly

History cannot be recovered, only accumulated

Nothing in this project can retrieve a minute older than the exchange's recent window. If the service is down for four days, those four days are gone. The measured 50 days of history exist only because the process ran continuously; the live instance now shows three markets frozen since June, whose missing minutes are unrecoverable.

A gap can be a source fact, not a collection failure

Hyperliquid does not guarantee a candle for every minute. Refetching a gap is safe but may not close it, so the same candidate can appear in every future report. There is no way in this codebase to tell "we missed it" from "it never existed".

The rate budget is a local promise, not a contract

The exchange's 1,200 per minute ceiling applies to everything leaving the internet address, not just this process. The bucket assumes it is the sole consumer. Sharing the address with another tool silently overspends, and the bucket has no way of knowing.

Nearly one minute in five has no trades

2,380,174 of 13,002,252 stored rows have trades = 0. These are valid exchange output with a carried-forward price, but any volatility, return or liquidity calculation that treats them as genuine observations will understate movement. The collector stores them faithfully and does not flag them beyond the trades column.

Volume is not comparable across markets

The volume column is quantity of the underlying asset, not dollars. One unit of BTC volume and one unit of DOGE volume are worth wildly different amounts. A rough dollar figure is $\text{notional} = v \times c$, where $v$ is the volume column and $c$ the close. Worked from the sample above: $1.29563 \times 63{,}976 = 82{,}889$ USDC for that one minute. There is no such column in the table; the caller must compute it.

Failure counting is pessimistic and one-dimensional

A market that succeeds in phase 2 but fails during gap repair is counted as failed, so symbols_ok can understate what was actually collected. And a run that fails entirely writes no ingestion_runs row at all if the cycle throws before reaching the metadata write — the absence of a row is itself the signal, which is easy to miss.

The horizon setting and the alert thresholds are not linked

rest_horizon_candles = 5000 and alert_critical_min = 4320 are related by arithmetic but not by code. Changing one without the other silently moves the alarm to the wrong side of the point of no return.

Running it yourself

uv sync, then cp .env.example .env and fill in the ClickHouse values. uv run hyperliquid-candles-run-once performs one cycle, uv run hyperliquid-candles starts the service, and uv run hyperliquid-candles-quality prints the report. In this environment the test suite needed uv run --with typing_extensions pytest, because the installed anyio version imports typing_extensions unconditionally while declaring it only for older Python versions. That is a packaging quirk of a dependency, not a fault in this project.
